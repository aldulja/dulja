# Phase 6 plan reconciliation — 2026-10-07

Read-only review of the supplied plans against the merged Phase 5 implementation identified the corrections below. These are implementation requirements to prove with regressions, not claims that their runtime paths already pass. Task status and executed checks live in `docs/reports/phase-6.md`. These corrections are now implemented; the slice exit records distinguish executed proofs from external gates.

## 6A enrolment response cache

Ordinary idempotency caching persisted the successful enrolment-issuance response, including its plaintext bearer code. Plan Contracts §4.2.9 and proposed amendments to ADRs 0055/0020 now register exactly this successful issuance as a one-time secret response: return 201 once, atomically store only a safe 409 problem for retries, and preserve ordinary failed-response caching, hash checks and reclaim behavior. Prove plaintext absence in the cache and safe replay after authority removal, including equivalent encoded paths. A lost first response requires a fresh enrolment and terminal code.

## 6B durability, acknowledgements and money

- Use the actual `Money.allocate(readonly bigint[], mode)` API; plan snippets accepting string weights without a mode are stale.
- Persist catalogue rows and every stream cursor atomically in one SQLite transaction. A page is globally ordered; advancing only touched streams prevents resume. Acknowledge outbox rows by kind and ref, and serialize sync-loop calls. Do not merge ticket, shift and till-event refs into one acknowledgement set.
- SQLite WAL with `synchronous=NORMAL` can lose previously committed sales after power loss. Use FULL for the sale/outbox durability guarantee, and preserve atomic ticket completion plus outbox insertion. The on-account path also needs an outer transaction, rather than selling and completing in separate autocommits.
- Account sales are required by spec §3.7.6 but the 6A draft rejects zero tenders and its policy has no receivable residual. Reconcile the customer-required account-sale path, posting policy and current server credit controls before accepting these tickets; preserve the one posting service.
- Rebind transport and serialized sync loops after successful first enrolment. The supplied `openTill` constructs a null transport and never installs the callback that replaces it, leaving sync disabled until restart.
- Prove a sale's transaction with a real injected outbox-write failure; the supplied nominal rollback test does not trigger that failure. Ticket, lines, outbox and attendance must roll back together.
- Automatic cash-rounding discounts also encounter server authority and branch discount limits. Proposed ADR 0059 now specifies optional verifiable `cashRounding` evidence, reconstruction of manual discounts and exact branch-policy/tax/tender checks. Register that additive wire/schema/domain-function correction during 6C before implementation. Test zero/tight limits, forged evidence and manual discounts hidden by cancellation; no unchecked flag bypasses authority.
- Promotions meet the same authority and limits (2026-10-23 plan audit). 6B Task 6 says the branch limit reads the cashier's discount alone, but its snippets limited the line's whole discount, promotion included, at the till and the server. ADR 0059's PR 12 review amendment applies the cash-rounding pattern: optional `TicketLine.promotion` evidence that the server recomputes through the shared domain `promotionDiscount`. A price override is promoted at the overridden (wire) price. 6B Task 5 Step 4's text comparison of the mirrored window against `toISOString()` is replaced by an instant comparison (`promotionActiveAt`). The text comparison dropped a promotion at its last instant and shifted a non-UTC session's windows.
- Preserve quick-created customer data during tender reconstruction. Rebuilding a ticket with `newCustomer: null` loses the offline party payload.
- The merged 0055 contains only the document-line tax FK; 6B registers the missing item assignment in its allocated 0063 migration, truthfully named `0063_alter_item_seed_permission_phase6b.sql`. Party-specific price lists already landed in 0045: implement the pricing case without a skip or another column. Preserve explicit null tax assignments once `item.tax_code_id` exists. Do not replace them with a company default through `??`, or turn a missing/expired referenced code into an untaxed wire line. Cash rounding must use each ticket line's pinned tax selection consistently rather than recomputing from the current item while retaining the old ID.
- Referenced returns must preserve original price, discounts and rounding/tax facts. Match original lines unambiguously, including duplicate items, and aggregate requested quantities so duplicate return rows cannot exceed the original quantity. Prove refund values and ledger/tax tie-outs with adversarial fixtures.
- Copy or embed the SQLite schema in the POS main-process build; a CJS bundle cannot rely on the plan’s source-relative `import.meta.url` lookup. Keep the built POS main process and external native dependencies in a layout where Node can resolve `better-sqlite3`. Separate POS `app.setName` and `extraMetadata.name` so user-data and updater-cache paths do not share the back-office name.
- Preserve the desktop's proven `npmRebuild: false` N-API native-module configuration. The copied true setting would invoke an unnecessary MSVC rebuild. Verify the packaged native load on Windows; Linux build checks do not prove Windows execution.
- Task 11 Step 6's sample (`tests/e2e/pos-rtl-parity.spec.ts`, 2026-10-23 plan-gap fix) launches `pos.exe` through `_electron` and visits `#/login`, `#/sell`, `#/tender` and `#/price-check`. The till has no hash routes; it moves between state views, and a cashier reaches each by its key. The packaged till is Windows-only and starts unenrolled, so the ubuntu `e2e` job cannot launch it. The spec therefore serves the built `apps/pos/dist` in Playwright's Chromium through the desktop's own `resolveRendererRequest`, under the desktop's `CONTENT_SECURITY_POLICY` and at its 1280×800 window. It answers `window.dulja.pos` from the built `pos-main.cjs` that `main-pos.ts` loads, over the fourteen `POS_CHANNELS`, with an enrolled in-memory till, and a second, unenrolled one for the enrol form. Each view is measured in both directions, and a sale is completed by keyboard. The packaged launch stays with CI's Windows `desktop` job. The spec makes the back office's test 23 checks of the till, not only layout: one numbering system per screen, no string left in the other language, and the same things and figures when the same state is switched to the other language. The views it does not visit are listed in its header. Decision recorded with it (2026-10-23 review repair): the Arabic `pos.shortcuts` names the keys as the keyboard prints them (`F2`, `F4`, `F8`, `F10`, `Esc`), as the English does. It had read "key 2" … "key 10" in Arabic-Indic digits, which sent a cashier to the digit keys and put a second numbering system on every signed-in screen.
