# POS till

The POS is a separate Windows application with its own user-data directory and updater cache. Build it with `bun run --filter @dulja/desktop build:pos`; package the unsigned x64 installer with `DULJA_API_BASE_URL=https://<api-host> bun run --filter @dulja/desktop dist:pos`. The installer is `dulja-pos-<version>-windows-x64.exe`; `release.yml` builds it (a `v<semver>` tag, or a `preview` dispatch). The packaged native-module check runs on Windows CI. Linux unit tests and the isolated Node bundle proof do not establish Windows execution or printer operation.

The API address is baked into the package when it is built (ADR 0093): the build reads `DULJA_API_BASE_URL` (the repository variable of the same name in `release.yml`) and ships it as `resources/pos-config.json`. It must be `https://`. An installed till never reads the environment; one built without an https origin refuses to start and says why. To point tills at a different server, install a build made for it. `DULJA_API_BASE_URL` in the environment is honoured only by an unpackaged development run (`start:pos`), which falls back to `http://127.0.0.1:3000`. Enrol using a valid terminal enrolment code, then pull the catalogue. The main process encrypts the terminal key using Electron safeStorage; the renderer cannot read that store. The till checks for a new version 30 seconds after it starts and every four hours, downloads it, and installs it the next time it quits. A missing or unreachable feed is logged and nothing else. Do not replace an enrolled device while it has an open shift or pending messages. Keep a backup of the entire POS user-data directory when recovering a till; deleting its SQLite file discards unsent business records.

Choose English or Arabic, sign in with an employee number and PIN, and open a shift with the actual opening float. Scan a barcode or search an item, adjust quantity, then review and pay. F2 opens price check, F4 customers, F8 review, F10 shift and Escape returns to selling. The default cash payment follows the branch increment; card and other tenders use the original ticket amount. Mixed tenders, references, handed cash and change are preserved. The receipt uses the client reference until the server acknowledges its document number. Printing uses the normal Windows printer driver.

A referenced return must load a completed receipt from this till and retains that sale's price and tax facts. A missing original cannot silently become a blind return. Blind returns, discounts, price overrides, customer creation and on-account sales require their own cached grants and limits. Supervisor approval requires a different employee's PIN and a reason. The server verifies live authority again on reconnect.

Unpaid reviewed tickets survive restart. Finish or cancel the recovered ticket before starting another ticket or closing the shift. Cancellation requires a reason, preserves the local ticket and audit, and removes only its unsent draft intent. The status indicator shows catalogue arrival, revision, pending messages and connection state. A queued or rejected batch remains pending; pulling a new catalogue and draining again may resolve it. Do not delete outbox rows to clear an error. Send the client reference and displayed refusal to the administrator for resolution.

The shift screen records no-sale and drawer-open events and accepts the physical cash count. A live manager with close_any can close another cashier’s shift on this till. Close submission waits for the shift’s ticket/event acknowledgements; the server derives expected cash and posts a nonzero over/short through the ordinary posting service. The local settled tender totals remain a counting aid.

A financial void needs an acknowledged ticket in the current open shift, a reason, the cashier’s void grant and a different supervisor PIN when the branch cap requires it. It queues a reversal request and retains the completed local sale until the actual event acknowledgement. A ticket with a return cannot also be voided; a pending void prevents a return from the same source. Refusals remain visible and pending.

In the back office, open Shift register, choose company/branch/dates and activate a shift by keyboard or its terminal button. The Z-report shows posted ledger tenders, other cash movements, the count and over/short, and drawer events. Print report uses the normal print dialog. The view selector also exposes sales by cashier, including differences attributed to a manager who closed without selling. Paid-outs, safe drops and banking remain excluded under the recorded OD-10 default. Installer signing, deployment and actual shop printer verification remain external gates.
